# 票券規則稽核（2026-08-06）

> 使用者提問：「把現在的票券使用規範再拿出來看一次，列清楚規則，看看有哪邊又有可能因為
> 退票／退課／取消／新增，會有票券混亂、超約的問題發生。」
>
> 以下規則**全部照實際程式碼整理**（不是設計文件），每條都附函式名，方便對照。

---

## 一、現行規則

### 1. 這張票能不能用在這堂課（`tkFitsBooking`）

依序檢查，任何一項不過就出局：

| # | 檢查 | 說明 |
|---|---|---|
| 1 | `tkUsableBy` | 持有人或共享者 |
| 2 | `status==='usable'` 且 `sessions_remaining>0` | 作廢／用畢／餘額 0 出局 |
| 3 | `tkOverBooked` | 已排滿總堂數就不能再排（**超約防線**） |
| 4 | `tkUnlockedLeft>0` | 分期票：未繳期數的堂數不能預約 |
| 5 | `expire_date >= 上課日` | 過期票不能用在之後的課 |
| 6 | `start_date <= 上課日` | 還沒開始的票不能用在之前的課 |
| 7 | `tkTimeOk` | 限時段票（友善）只能平日 18:00 前 |
| 8 | 類別比對 | 團課／自主訓練＝同類別即可；其他類別嚴格比對票種 |

### 2. 自動挑哪一張（`listUsableTickets` 的排序）

1. 限時段的票（友善）最先 —— 最容易白白過期
2. 30 天內到期的 → 依到期日先用
3. 其餘照購買順序（＝票券編號）先進先出
4. **（2026-08-06 新增）** 取消後重約同一天同一種課 → 優先用回剛被退回的那張（`rebookSameDayTicket`），排在「櫃檯指定」之後、一般自動挑票之前

### 3. 扣與退

- `deductTicket`：`sessions_remaining -= 1`、首堂順便開通效期、寫 `ticket_logs.deduct`
- `refundTicket`：`sessions_remaining += 1`、`used_up` 轉回 `usable`、若該票已無有效預約則把效期退回未開通、寫 `ticket_logs.refund`
- 團課退票找哪一張：`grpNetDeductTicket`（該堂**淨扣課 > 0** 的票，取最近扣的那張）

### 4. 「這堂課用了哪一張票」的三個來源（`buildWallet`）

| 順位 | 來源 | 性質 |
|---|---|---|
| ① | `bookings.ticket_id` | 單人課預約當下就綁 —— **事實** |
| ② | `ticket_logs` 的扣課紀錄 | 團課走這條（一堂多人、逐名額各扣各的）—— **事實，但取消/重約會重排** |
| ③ | 先進先出推算（`allocBookingsToTickets`） | 舊系統匯入的課①②都沒有 —— **猜的** |

補充規則：補課券不參與③（它一定有扣課紀錄）。

### 5. 團課的特殊性

- 預約**不寫 `ticket_id`**（一堂多人，欄位放不下），只靠 ②
- 逐名額：同一人可佔多個名額，一個名額扣一堂（`seatKeys` / `id#2`）
- 出席狀態逐名額記在 `attendance`

### 6. 請假／取消未退／補課券（2026-08-06 定案）

- 請假：本堂票**照扣不退**、另發補課券（效期自**開課日**起算 14 天，自主訓練類 7 天）
- 票券夾把請假算成「已用一堂」，圓點**實心紅**
- 取消時選「扣課不退」：同樣算已用一堂，圓點也是實心紅
- 整堂取消 → 收回這堂發過、**還沒用**的補課券
- 教練人次不含請假名額（`grpHeadsNoLeave`）

### 7. 顯示（`buildWallet.slotOf` / `ticketTokens`）

- 已用堂數 `used` 取三個訊號的**最大值**：①直連且已簽到 ②蓋在這張票上且已簽到（含請假／取消未退） ③帳面已用（總 − 餘額 − 待上）
- 圓點依**上課日期**排（2026-08-06 起），狀態各自上色
- 票券堂數不夠放的已預約課 → 紅虛線「需補票」

## 二、風險點（可能造成混亂／超約）

### 🔴 R1 團課的超約防線形同虛設

`tkOverBooked` 靠 `tkBookedCountMap`，而它只數 `bookings.ticket_id` —— **團課預約沒有這個欄位**。
結果：團課能不能再約，只剩「`sessions_remaining>0`」這一道，而餘額正是最常被匯入批次校正、
最容易與實際上課紀錄脫節的欄位。

> 影響：餘額被校正成偏多時，團課可以一直約下去，票券夾才會事後畫出紅虛線超約圈。

### 🔴 R2 兩套「已用」口徑長期並存

- 帳面：`sessions_total − sessions_remaining`
- 戳記：實際課卡數（含推算）

7/26、7/29 兩次批次校正動的是**帳面**，戳記沒動。於是像林紫錡 `MTK-E52631B15156`
會出現「卡片顯示 5/5 用畢，資料庫餘額還有 1」。`slotOf` 取最大值只是讓畫面自洽，
沒有解決兩邊不一致。

> 影響：可約堂數與畫面不一致；作廢／續約判斷可能踩到錯的那一邊。

### 🟠 R3 `deductTicket` 不看餘額、`refundTicket` 不封頂

- 扣：不檢查 `sessions_remaining>0`，可以扣成**負數**（一般路徑有 `tkFitsBooking` 擋，
  但「櫃檯指定票券」以外的補綁、批次、轉正等路徑是直接呼叫）
- 退：不檢查上限，重複取消／重複呼叫可以讓餘額**超過總堂數**

### 🟠 R4 推算（③）每次重算

先進先出是「當下重算一次」，不是存下來的事實。任何一筆新增／取消／退票，
都可能讓一整批歷史戳記換到別張票上 —— 這就是「修 A 壞 B」的主要來源。
（櫃檯手動做的「補連結」其實就是在把推算固化成事實。）

### 🟠 R5 取消有兩條路，規則不同

| 路徑 | 誰在用 | 團課處理 |
|---|---|---|
| 前端 `cancelBooking` | 櫃檯／教練 | 逐筆比對 deduct/refund 後退款 ✅ |
| RPC `fn_cancel_booking` | 會員自行取消、單人課自動政策 | **只在 `ticket_id` 非 null 時退款** —— 團課會不退 |

目前前端有擋（`cancelRpcEligible` 排除小班肌力），但這是靠呼叫端自律，不是 DB 端保證。

### 🟡 R6 作廢（`voidTicketDo`）看不到團課的使用

作廢前的檢查是「`used>0` 或有 `b.ticket_id===此票` 的預約」。團課預約沒有 `ticket_id`，
所以只剩 `used` 這道；若餘額剛被校正成滿的，這張票可以被作廢，把已上的團課變成孤兒。

### 🟡 R7 更換票券中途失敗會多扣

`_doBkTicketChange` 是「先扣新的、再退舊的」（刻意選擇：寧可多扣看得到）。
退舊失敗只跳 toast，沒有補償機制，也沒有留下待處理清單。

### 🟡 R8 會員只能自行取消單人課

`memCancelBooking` 要求 `b.member_id===SESSION.id`，團課的 `member_id` 是 null →
會員端取消團課會顯示「找不到預約」。名額釋出只能靠櫃檯。

### 🟢 R9 補課券的邊角

- 請假 → 發券 → 券已用去補課 → 整堂又被取消：券**不收回**（保守原則，正確但要知道）
- 事後補發久遠的課：效期自開課日起算，可能一發下去就過期（視窗已有紅字警示）

## 四、建議的收斂順序

1. **把推算固化成事實**（對應 R4）：跑一次批次，把目前推算出來的歸屬寫成
   `delta=0` 的「補連結」扣課紀錄，設一個切分日；之後③只作用在切分日以前。
2. **團課補上超約防線**（對應 R1）：`tkBookedCountMap` 併入 `ticket_logs` 的淨扣課，
   讓 `tkOverBooked` 對團課也有效。
3. **扣／退加護欄**（對應 R3）：扣到 0 以下、退到超過總堂數時擋下並寫警示紀錄。
4. **每日對帳巡檢**（對應 R2）：總數／餘額／戳記／扣課紀錄四者對不上就在票券卡標警示，
   由系統先講，而不是等櫃檯看到怪畫面。
5. **中期**：團課的「名額 ↔ 票券」寫進資料（`attendance` 已是逐名額物件，
   再加一個同結構的 `seat_tickets`），③ 整條退場。
