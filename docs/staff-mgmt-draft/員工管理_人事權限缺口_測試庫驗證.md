## 1. 測試庫與正式庫的落差（先補齊才驗得準）
測試庫原本缺：員工守衛觸發器 `fn_employees_guard`、`salary_history` 表、員工表 4 欄（avatar_url、duty_order、duty_matrix、line_notify）、出勤表 3 欄（note、fixed_by、fixed_at）。內容取自正式庫定義（唯讀），已補進測試庫。
另外：測試庫沒有 `fn_set_employment_type`，所以「主管調整僱用別」那條窄門**無法在測試庫實測**（它是 SECURITY DEFINER，理論上不受 RLS 改動影響）。測試庫出勤表政策與正式庫不同（`att_self`/`att_staff` vs `att_admin`/`att_self_*`/`att_staff_read`），本次不動出勤政策，核准 RPC 以 SECURITY DEFINER 寫出勤，不受影響。

## 2. 各角色驗證結果（假資料、各角色以偽造 JWT 實際執行）
角色：管理員、櫃檯（role=front_desk）、一般教練、主管甲（管 e_c2）、主管乙（管 e_c3）、薪資人員（front_desk，僅授予 pay_view）。

## 3. 建議修改（內容見 migration）
1. 新表 `hr_grants`（職責：pay_view / pay_adjust / pay_publish / insure / employment / leave_settle）、`manager_scope`；函式 `has_hr_duty()`、`has_any_hr_duty()`、`is_my_report()`。
2. 補打卡：政策改為「本人／櫃檯只能新增 pending」「讀取依本人／櫃檯／所管主管」「改寫僅管理員」；新增 `requested_by`、`reviewed_by`；核准／駁回改走 RPC `fn_punch_decide`（管理員或所管主管；同一套工時算法：0.5 小時為單位、跨午夜加 24 小時）。
3. 員工表：基表只給管理員、有人事職責者、本人；新增 `employees_public`、`employees_manager_scope` 兩個檢視；更新政策改為管理員或本人。
4. `salary_history`：讀取改為 `has_hr_duty('pay_view')`（本人 `sh_self` 不動）。

## 6. 待你決定／風險
1. **薪資人員讀得到整列**：資料庫無法只開「底薪」而不開身分證、銀行（Postgres 沒有欄位層 RLS）。要真正分開，需把薪資／證件／銀行／投保拆表（前次報告的方案 A）。目前只能做到「讀整列需有人事職責」。
2. **管理員過渡期一律通過**（`has_hr_duty` 含 `is_admin()`）：維持現行營運；日後要「系統管理員預設沒有人事權限」，只要拿掉函式內那一行。
3. **管理員可核准自己的補打卡**（正式庫有 2 位在職管理員，可改成一律不可自核，請你決定）。
4. **主管範圍資料**：須先指定（正式庫 2 位主管、1 位櫃檯）。
5. 本次**沒處理**但發現：員工本人對自己的出勤（attendance）有直接新增／修改權限（打卡所需），技術上能改自己的上下班時間；薪資發布（`pay_publish`）、休假申請、月結工時確認還沒有資料表，屬後續批次。
6. 前端要先改完並在測試庫整體驗收（各角色登入走過教練名單、排班、薪資頁、補打卡），才能對正式庫提出套用申請。
